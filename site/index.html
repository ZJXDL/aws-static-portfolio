01THE SYSTEM

A SIMPLE SITE, A REAL CLOUD BOUNDARY

One public door.
One private source.

Visitors connect to CloudFront. The S3 bucket has no public access; only this CloudFront distribution can read the site files.

01

The browser connects

CloudFront accepts the request over HTTPS and checks whether a fresh copy is already cached nearby.

02

The edge checks the origin

On a cache miss, CloudFront signs its request with Origin Access Control (OAC) and AWS Signature Version 4.

03

S3 checks who is asking

The bucket policy allows reads from this distribution only. CloudFront returns the file and can cache it for the next visitor.

“

IN EVERYDAY WORDS

The files are in a locked archive. CloudFront is the staffed front desk: it can fetch a file from the archive, then keep a nearby copy ready for the next visitor.

That’s the idea behind a private S3 origin.
↳

Why not S3 website hosting? This setup uses the regular S3 API endpoint, so CloudFront can authenticate to the private bucket with OAC. S3’s website endpoint does not support OAC.

02THE RELEASE

FROM A COMMIT TO A LIVE CHANGE

No long-lived keys.
Just a trusted workflow.

A change to the site starts a GitHub Actions workflow. AWS checks who the workflow is before granting short-lived permission to publish.

01

Change

Edit HTML or CSS in site/ and push to main.

02

Prove identity

GitHub presents an OIDC token tied to this repository and branch.

03

Get temporary access

AWS validates the token, then grants the workflow a limited IAM role.

04

Publish

Files sync to S3; CloudFront clears its cache so visitors get the update.

✓

Credentials expire automatically. The publishing role can change website files and request a cache invalidation; it cannot change the AWS infrastructure.

More about the AWS trust and deployment permissions

The workflow requests an OIDC token with audience sts.amazonaws.com. The IAM role trust policy limits access to this repository’s main branch.

Its permissions are scoped to listing and updating this site’s S3 bucket and creating invalidations for this CloudFront distribution. The OIDC provider and deploy role were configured in IAM outside the ten OpenTofu-managed resources.

03THE BUILD

INFRASTRUCTURE AS CODE

Small stack.
Specific safeguards.

OpenTofu describes the AWS resources in reviewable files. Applying the same configuration can recreate the stack.

A

STORE

S3 bucket

Private object storage for the HTML, CSS, and other site files.

  • All public-access blocks enabled
  • Bucket-owner ownership; ACLs disabled
  • AES-256 encryption and versioning
  • Old versions expire after 30 days
B

DELIVER

CloudFront

A global content delivery network in front of the S3 origin.

  • HTTPS enforced; TLS 1.2 or newer
  • OAC signs requests to S3
  • Compression and caching enabled
  • Security headers added to responses
C

AUTHORIZE

Bucket policy

A single, explicit rule connects the public delivery layer to private storage.

  • Allows s3:GetObject to CloudFront
  • Requires this distribution’s ARN
  • No anonymous read permission

BROWSER SAFEGUARDS

Responses include HSTS, clickjacking protection, MIME-sniffing protection, a Content Security Policy, and a referrer policy. These headers reduce common browser-side risks; they do not replace application security.

WHAT THIS PROJECT DOES NOT INCLUDE

Remote state
OpenTofu state is local. A team deployment needs protected remote state, locking, and backups.

Custom domain
The site uses CloudFront’s default address. A domain would need DNS and an ACM certificate.

Application backend
This is a static site, with no API, database, login, or dynamic content.
